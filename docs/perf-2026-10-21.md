# Live performance, 2026-10-21

Savanna (`scenarios/savanna.yaml`, 20 drones, `dt` 0.1 s), Apple M3 (8 cores, 16 GB), Webots R2025a. Measured with `earshot live --profile` (the world's per-tick split) and `tools/measure_live.py` (from outside: real-time factor, GPU, CPU; `--views` keeps the four view cameras on as an open HUD does). 80-120 sim s per run, first 15 s skipped. No other earshot process ran, except the last row (a 4-job savanna eval in another session).

## Result

Superseded by [the speed-up below](#speed-up-evening-webots-nightly): 1.00x with the Webots window in front, on the Webots nightly. The morning's measurements:

Only Webots in fast mode, without its 3D window and without views, keeps real time. The demo as `earshot live --backend webots` starts it runs at about 0.42x.

| Setup | Real-time factor | Webots step ms/tick | Notes |
|---|---|---|---|
| twin2d | 1.0 | - | world 15-20 ms/tick, ~60 ms slack; agents not a bottleneck |
| Webots realtime, views on | ~0.5 (profile) | 127-141 | freezes inside `sup.step`: 25, 57, 83, 226 s |
| Webots realtime, views off | 0.44 | 95-140 | freezes up to 30 s |
| Webots fast, 3D window, views on | 0.44 | 146-162 | GPU 75-83 %, Webots CPU 69 % |
| Webots fast, 3D window, views off | ~0.6 (profile tail) | ~108 | the window redraws every basic step |
| Webots fast, no window, views on | 0.77 | 54-64 | no freezes |
| Webots fast, no window, views off | 0.98 | 29-33 | 15-25 ms pacing slack left |
| Webots realtime, views on, Webots in front | 0.42 | ~42 + waits | no long freeze, stalls up to 2 s (one run, eval in parallel) |

Our own per-tick cost in Webots runs (ms): `wb.push` (setting poses, 5 basic steps per tick) 10-35, view JPEGs 8-11, drain 4-10, publish ticks 3-12, snapshot 2-6, twin 2-5.

## Why

1. Realtime mode cannot keep pace: Webots spends the full wall-clock time of each step itself, and our ~40 ms per tick comes on top, in series.
2. Pose writes: every Source (parked ones too), every drone, CAMV and the view cameras are written on each of the 5 basic steps per tick (`basicTimeStep 20`).
3. The four view cameras cost ~25-30 ms of Webots step per tick (offscreen), the 3D window more.
4. JPEG encoding of the views runs inside the tick loop.
5. The long freezes appear only in realtime mode; probably macOS App Nap throttling Webots in the background (not confirmed).

## Speed-up (evening, Webots nightly)

Branch `claude/webots-speedup-75bd8e`, one commit per change. Measured on the Webots R2025a nightly of 21 Oct 2026 (c22f0ef; the release cannot open its controller port on macOS 27, Webots issue #6976, fixed in PR #7032), macOS 27.0.1, load average ~3, no other earshot process. Savanna, realtime mode with the 3D window, views on (`measure_live.py --seconds 50 --skip 15 --views`), one run per row in a single series; "front" is the app in front during the run, logged every second (`lsappinfo front`).

Reading it:
- **`basicTimeStep` 50 is what keeps real time**: in realtime mode Webots spends each basic step's wall time and redraws its window every step; 2 steps per tick instead of 5 brings Webots' share from ~110 to ~85-95 ms. The overlap (fix 1) hides our ~10-15 ms of world work inside the last step; it saved 5-10 ms per tick, small next to five self-paced Webots steps, which is why the step length is the mover. All scenarios use `dt` 0.1, so 50 ms steps fit every world. Pose writes and JPEGs were already small (a few ms); they no longer show in the tick.
- **With the 3D window in front, the final version runs at 1.00x** (twice, 130 s each, with views on; one run added a live Source).
- **Slow phases with another app in front** (here the Claude app): in three runs Webots' own step grew to 150-230 ms per tick from about sim 60 s on, Two traced runs (Webots in front) had no drone flying after landing and no slow phase; the slow runs were not traced, so a flying drone in the main view's chase camera is unlikely as the cause but not excluded. Cause not pinned down (GPU contention with the app in front, or macOS throttling a covered window); it is Webots' step, not our code (`wb.push`, `wb.grab`, `views.jpeg` stay at 0-3 ms). Keep the Webots window in front for the demo; the excluded fixes (view-camera render settings, App Nap) are what is left if it must run covered.
- **Motion at 50 ms**: Webots shows poses at 20 Hz; a Verifier at 15 m/s moves 0.75 m per frame against km-scale terrain in the 3D window, and the HUD's main view samples at 10 Hz (100 ms) either way. Not judged by eye in a recording; 25 ms (4 steps per tick) is the fallback if it looks stepped.
- The earlier numbers (0.31x before, 0.75x with the overlap, release Webots) were taken under another session's evals and a 270 s stall; superseded by this series.
