# Live performance, 2026-10-21

Savanna (`scenarios/savanna.yaml`, 20 drones, `dt` 0.1 s), Apple M3 (8 cores, 16 GB), Webots R2025a. Measured with `earshot live --profile` (the world's per-tick split) and `tools/measure_live.py` (from outside: real-time factor, GPU, CPU; `--views` keeps the four view cameras on as an open HUD does). 80-120 sim s per run, first 15 s skipped. No other earshot process ran, except the last row (a 4-job savanna eval in another session).

## Result

Only Webots in fast mode, without its 3D window and without views, keeps real time. The demo as `earshot live --backend webots` starts it runs at about 0.42x.

| Setup | Real-time factor | Webots step ms/tick | Notes |
|---|---|---|---|
| twin2d | 1.0 | - | world 15-20 ms/tick, ~60 ms slack; agents not a bottleneck |
| Webots realtime, views on | ~0.5 (profile) | 127-141 | freezes inside `sup.step`: 25, 57, 83, 226 s |
| Webots realtime, views off | 0.44 | 95-140 | freezes up to 30 s |
| Webots fast, 3D window, views on | 0.44 | 146-162 | GPU 75-83 %, Webots CPU 69 % |
| Webots fast, 3D window, views off | ~0.6 (profile tail) | ~108 | the window redraws every basic step |
| Webots fast, no window, views on | 0.77 | 54-64 | no freezes |
| Webots fast, no window, views off | 0.98 | 29-33 | 15-25 ms pacing slack left |
| Webots realtime, views on, Webots in front | 0.42 | ~42 + waits | no long freeze, stalls up to 2 s (one run, eval in parallel) |

Our own per-tick cost in Webots runs (ms): `wb.push` (setting poses, 5 basic steps per tick) 10-35, view JPEGs 8-11, drain 4-10, publish ticks 3-12, snapshot 2-6, twin 2-5.

## Why

1. Realtime mode cannot keep pace: Webots spends the full wall-clock time of each step itself, and our ~40 ms per tick comes on top, in series.
2. Pose writes: every Source (parked ones too), every drone, CAMV and the view cameras are written on each of the 5 basic steps per tick (`basicTimeStep 20`).
3. The four view cameras cost ~25-30 ms of Webots step per tick (offscreen), the 3D window more.
4. JPEG encoding of the views runs inside the tick loop.
5. The long freezes appear only in realtime mode; probably macOS App Nap throttling Webots in the background (not confirmed).
